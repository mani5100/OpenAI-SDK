# PRD: Conversation AI Agent API (OpenAI SDK)

## 1. Introduction / Overview

This feature delivers an API-only conversational AI agent powered by the OpenAI SDK, hosted in a single FastAPI service. The primary users are internal developers who need a simple, reliable REST endpoint to send user messages and receive assistant replies. For the MVP, the service runs without authentication and does not persist data; session context is maintained in-memory only (ephemeral), suitable for a single-process/single-instance deployment.

Goal: Enable a minimal, production-conscious, internal API for chat that is easy to integrate (< 1 day), supports per-session short-term context, and clearly documents inputs/outputs and error modes.

Assumptions (for MVP):
- Conversation history: In-memory, keyed by `session_id`, with TTL and bounded message count. No disk/DB persistence.
- No authentication initially (internal network only). Future work may add API-key or OAuth2/JWT.
- No UI; API only with autogenerated Swagger docs.

## 2. Goals

- G1: Provide a single REST endpoint to exchange chat messages with OpenAI via the official SDK.
- G2: Support ephemeral per-session conversation context when a `session_id` is supplied.
- G3: Make model and basic generation parameters configurable (env defaults + per-request overrides).
- G4: Ship clear OpenAPI/Swagger docs and examples for junior developers to consume.
- G5: Handle common errors (timeouts, rate limits, invalid request) with consistent HTTP responses.

## 3. User Stories

- US1: As an internal developer, I can POST a message and receive an assistant reply so I can build internal features quickly.
- US2: As an internal developer, I can provide a `session_id` so the agent replies with short-term context across multiple turns (until TTL/eviction).
- US3: As an internal developer, I can override the default model and temperature per request to experiment with quality vs. cost/latency.
- US4: As an internal developer, I can read the API schema and examples in Swagger to integrate within an hour, without reading the code.

## 4. Functional Requirements

1. Endpoint: The system must expose `POST /api/agent/chat`.
   - Request body must accept:
     - `message` (string, required): the user's message.
     - `session_id` (string, optional): links exchanges to a short-lived in-memory history.
     - `model` (string, optional): overrides the default model for this request.
     - `system_prompt` (string, optional): additional system instruction for this request/session.
     - `temperature` (number, optional): generation control; default from env.
   - Response must return:
     - `reply` (string): assistant text.
     - `model` (string): model used.
     - `usage` (object, optional): token/cost-related fields if available from SDK.
     - `latency_ms` (number): server-measured completion time.
     - `session_id` (string, optional): echoed if supplied.
     - `truncated_history` (boolean): whether older turns were dropped due to limits.

2. OpenAI Integration: The service must call OpenAI via the official SDK using a server-side API key.
   - API key must be read from environment variable (e.g., `OPENAI_API_KEY`).
   - Default model and parameters must be configurable via env (e.g., `OPENAI_DEFAULT_MODEL`, `OPENAI_DEFAULT_TEMPERATURE`, `OPENAI_TIMEOUT_SECONDS`).

3. In-memory Session Context: When `session_id` is provided, the system must maintain short-term history in memory.
   - Bound history by maximum messages (e.g., last N user+assistant turns) and/or token budget.
   - Apply a TTL (e.g., 30 minutes of inactivity) after which history is discarded.
   - Indicate when history was truncated due to bounds.

4. Error Handling: The API must translate common errors to HTTP responses with stable shapes.
   - 400 Bad Request for invalid inputs or unsupported parameters.
   - 401 Unauthorized is not used in MVP (no auth); reserve for future.
   - 408 Request Timeout for upstream model timeouts if applicable.
   - 429 Too Many Requests: surface OpenAI rate limit; include `retry_after` when available.
   - 5xx: Map upstream/service failures to 502/503 with `error.code`, `error.message`.

5. Documentation: The service must expose interactive docs via Swagger (`/docs`) and ReDoc (`/redoc`).
   - Include clear request/response examples for the chat endpoint.

6. Configuration: The service must read configuration from environment with safe defaults.
   - Required: `OPENAI_API_KEY`.
   - Optional with defaults: `OPENAI_DEFAULT_MODEL`, `OPENAI_DEFAULT_TEMPERATURE`, `OPENAI_TIMEOUT_SECONDS`, `SESSION_TTL_SECONDS`, `SESSION_MAX_TURNS`.

7. Observability (MVP):
   - Log request start/end with correlation id (avoid logging full message content by default to reduce PII exposure; log sizes and timing instead).
   - Include structured logs for errors with stable `error.code` and `error.message` fields.

8. Security (MVP):
   - No external authentication required for initial release. Assume internal network usage only.
   - Do not include user content in logs by default; allow opt-in redaction/opt-out content logging for debugging.

9. Performance & Limits (MVP):
   - Reasonable defaults for timeouts (e.g., 30s) and response size; no streaming in MVP.
   - Basic token/context safety: trim oldest turns when exceeding bounds; surface `truncated_history=true`.

## 5. Non-Goals (Out of Scope)

- NG1: Web UI or frontend; only API is provided.
- NG2: Database persistence for chats; no Postgres/Redis/Vector DB in MVP.
- NG3: Moderation/PII redaction/advanced guardrails beyond OpenAI defaults.
- NG4: Tool/function calling, retrieval-augmented generation, or file uploads/ingestion.
- NG5: Multi-tenant auth, RBAC, or rate limiting at the gateway.
- NG6: Horizontal scaling across multiple instances (MVP is single-instance, in-memory state).

## 6. Design Considerations (Optional)

- API Shape:
  - `POST /api/agent/chat` with JSON body and JSON response.
  - Optional `session_id` enables contextual replies; omit for stateless single-turn.
- Session Store:
  - In-memory Python structure (e.g., dict keyed by `session_id`) with TTL and max turn count.
  - Single-process/single-instance only; future move to Redis for multi-instance.
- History Truncation Strategy:
  - Drop oldest turns when exceeding `SESSION_MAX_TURNS` or estimated token budget.
- Configuration Management:
  - Twelve-Factor style via environment variables.
- Logging:
  - Use structured logs; avoid storing raw prompts by default; include sizes and timings.
- Developer Experience:
  - Provide sample requests in Swagger examples for quick copy/paste.

## 7. Technical Considerations (Optional)

- OpenAI SDK: Use the official OpenAI Python SDK (latest stable). Keep model name configurable; ship a default via env (e.g., `gpt-4o-mini`, adjustable).
- Runtime: FastAPI app served by Uvicorn. Single-process for MVP.
- Timeouts/Retry: Configure client timeout; optionally implement brief retry with jitter for 429/5xx (cap at small attempts for MVP).
- Token Budgeting: Use light heuristics to avoid over-long history; precise counting may rely on SDK metadata when available.
- Windows-friendly development: ensure local run instructions work on Windows PowerShell.

## 8. Success Metrics

Proposed MVP targets (confirm or adjust):
- SM1: Developer integration time < 1 day using Swagger examples.
- SM2: P50 end-to-end latency < 3s for short prompts (< 300 tokens).
- SM3: < 1% request failures excluding network/credential errors during normal operations.
- SM4: Clear docs: at least one example request/response in Swagger that runs as-is.
